# 1부 · 경력자가 판단할 수 있어야 할 게임 프로그래밍 문제

## 1. 수명과 소유권 · 플레이어가 죽으면 어떤 데이터가 사라져야 하는가?

팀원이 쓰러졌다가 새 캐릭터로 부활합니다. 이때 점수까지 0점으로 돌아간다면 무엇이 잘못됐을까요? 점수를 죽기 전 캐릭터에만 저장했을 가능성이 있습니다. **객체의 수명**은 그 객체가 만들어져서 사라질 때까지의 기간입니다. 값을 어디에 저장할지 정할 때는 그 값이 언제까지 남아야 하는지 먼저 생각합니다.

탄창에 남은 탄약은 장비에, 부활 후에도 유지할 점수는 `PlayerState`에 둘 수 있습니다. 서버의 `GameMode`가 코어 확보를 판정한다면, 모든 플레이어가 볼 공동 진행도는 `GameState`에 두는 식입니다. `ActorComponent`는 여러 액터에서 장비 동작을 재사용할 때 유용합니다. 다만 소유 액터가 사라진 뒤에도 필요한 전적은 더 오래 유지되는 곳에 저장해야 합니다.

| 의도 | UE 표현 | 사례 |
|---|---|---|
| UObject가 다른 객체를 보유 | `UPROPERTY()`로 선언한 `TObjectPtr<T>` 멤버 | 장비 객체를 소유하는 인벤토리 |
| 사라질 수 있는 대상을 관찰 | `TWeakObjectPtr<T>` | 관전 위젯이 참조하는 Pawn |
| 아직 로드하지 않은 에셋 식별 | `TSoftObjectPtr<T>` | 상점의 고해상도 스킨 |

**관전 화면으로 확인해 봅시다.** A를 관전하다가 B로 시점을 바꿨는데 체력 바에는 여전히 A의 체력이 보입니다. A가 아직 월드에 남아 있다면 포인터 유효성 검사도 통과합니다. 이때 확인할 것은 ‘A가 살아 있는가?’에 이어 ‘체력 바가 지금 누구의 변경 알림을 받고 있는가?’입니다. A의 알림 등록을 해제하고 B에 등록한 뒤, B의 현재 체력을 한 번 읽어 표시합니다.

## 2. 상태 기계와 불변조건 · 두 플레이어가 같은 코어를 확보하면?

두 사람이 코어 A를 동시에 밟아도 확보 개수는 하나만 올라가야 합니다. 이처럼 입력이 어떤 순서로 들어오든 지켜야 하는 규칙을 **불변조건**이라고 합니다. 이 미션에는 두 가지가 더 있습니다. 진행 중일 때만 코어를 확보할 수 있고, 한 판에서 완료 상태로 넘어가는 일은 한 번뿐입니다.

아래 함수는 서버가 플레이어의 거리와 권한, 코어의 유효성을 확인한 뒤 게임 스레드에서 호출합니다. `Captured`는 이미 확보한 코어 ID의 집합입니다. 미션 시작 전에 목표 개수(`RequiredCount`)가 양수인지 검사하고, 새 판을 시작할 때 집합과 미션 단계를 함께 초기화합니다.

```cpp
ECaptureResult FMissionProgress::Capture(FName coreId)
{
    if (Phase != EPhase::Active || Captured.Contains(coreId))
        return ECaptureResult::Ignored;
    Captured.Add(coreId);
    if (Captured.Num() < RequiredCount)
        return ECaptureResult::Progressed;
    Phase = EPhase::Completed;
    return ECaptureResult::Completed;
}
```

**코드를 따라가 봅시다.** 목표가 두 개일 때 A, A, B, B 순서로 입력해 보세요.

| 입력 | 결과 | 이유 |
|---|---|---|
| 첫 번째 A | `Progressed` | 하나를 확보했고 목표까지 한 개가 남았습니다. |
| 두 번째 A | `Ignored` | 이미 집합에 있는 코어입니다. |
| 첫 번째 B | `Completed` | 서로 다른 코어 두 개를 확보했습니다. |
| 두 번째 B | `Ignored` | 미션이 이미 끝났습니다. |

세 가지 결과를 구분하면 호출한 쪽에서 진행 표시와 완료 보상을 따로 처리할 수 있습니다. 이 함수만으로 서버 재시작 뒤의 중복 지급까지 막을 수 있을까요? 그 문제는 5장에서 살펴봅니다.

## 3. 복제와 시간 · 완료 직후 들어온 사람은 무엇을 알아야 하는가?

플레이어가 ‘코어를 확보하겠다’고 보내는 것은 **명령**입니다. 서버가 판정한 ‘현재 2개 중 2개 확보’는 **상태**이고, 마지막 코어를 확보한 순간은 **이벤트**입니다. 중간에 합류한 사람도 알아야 하는 정보는 현재 상태로 남겨야 합니다. 이미 접속해 있던 사람에게 보낸 `Reliable RPC`를 나중에 들어온 사람이 다시 받아 보지는 않습니다.

언리얼이 서버의 값을 클라이언트에 전달하는 과정을 **복제**라고 합니다. 서로 다른 속성의 복제 알림 함수(`OnRep`)가 내가 기대한 순서로 실행된다고 가정하면 화면에 이전 목표와 새 진행도가 섞일 수 있습니다. 함께 읽을 미션 단계와 코어 개수를 한 구조체에 담으면 이 문제를 줄일 수 있습니다. 다른 액터의 준비 시점은 별도로 확인해야 합니다.

```text
의사코드 · 로컬 HUD와 모델이 모두 준비되는 시점에 실행
기존 구독 해제 → 새 모델 변경 알림 구독 → Render(모델의 현재 스냅샷)
상태가 바뀌면 Render(새 스냅샷)
HUD 비활성화 또는 대상 교체 시 기존 구독 해제
```

여기서 **스냅샷**은 화면을 그리는 데 필요한 현재 값의 묶음입니다. HUD가 늦게 열렸다면 스냅샷을 한 번 읽는 것만으로 2/2를 표시할 수 있습니다. 반대로 HUD가 먼저 열렸다면 모델이 준비되는 시점에 연결해야 합니다.

**확인 문제**　옵션을 닫을 때마다 미션 완료음이 다시 들립니다. `Render` 안에서 완료음을 재생하고 있지 않은지 확인해 보세요. 화면은 같은 값으로 여러 번 그릴 수 있지만, 소리는 완료 순간에 한 번 들려야 합니다.

## 4. 비용 모델과 측정 · 적 1,000마리의 표적 탐색을 최적화해야 할까?

적 1,000마리가 매 프레임 플레이어 네 명과의 거리를 각각 구한다면 거리 계산은 4,000번입니다. 그런데 실제로 시간이 오래 걸리는 부분은 그다음에 수행하는 시야 검사일 수도 있습니다. 거리 계산과 시야 검사 시간을 나눠 재야 어느 쪽부터 고칠지 알 수 있습니다.

위치처럼 함께 읽는 값을 메모리에 연속해서 배치하면 CPU가 가까운 데이터를 다시 활용하기 쉽습니다. 이를 **데이터 지역성**이라고 합니다. 대신 적을 제거하거나 옮길 때 저장 위치와 개체 ID의 대응을 유지해야 합니다.

60fps를 유지하려면 한 프레임에 약 16.67ms를 쓸 수 있습니다. 게임 스레드가 11ms, GPU가 19ms를 썼다고 해서 한 프레임이 곧바로 30ms가 되지는 않습니다. CPU와 GPU가 서로 다른 프레임을 겹쳐 처리할 수 있기 때문입니다.

같은 빌드에서 카메라 위치와 적 수를 고정하고 Unreal Insights로 실행 기록을 비교하세요. 평균뿐 아니라 **p95 프레임 시간**도 봅니다. 이는 프레임 시간을 짧은 순서로 늘어놓았을 때 약 95% 지점의 값입니다. 처음 에셋을 불러올 때 한 번 크게 끊기는 현상은 별도로 살펴야 합니다. 거리 검사 비용이 절반으로 줄어도 GPU가 계속 19ms를 쓴다면 최종 프레임 시간의 개선은 작을 수 있습니다.

[Robert Nystrom · Data Locality](https://gameprogrammingpatterns.com/data-locality.html) · [Epic · Unreal Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-insights-in-unreal-engine)

## 5. 멱등성과 영속성 · 구매 성공 직후 응답이 사라지면?

상점에서 스킨을 샀는데 응답이 오기 전에 연결이 끊겼습니다. 플레이어는 실패했다고 생각하지만 서버에는 이미 스킨이 지급됐을 수 있습니다. 같은 구매 요청을 다시 보내도 잔액과 아이템 수량이 한 번 구매했을 때와 같게 유지되는 성질을 **멱등성**이라고 합니다.

여기서 상품 ID만 비교하면 같은 스킨을 새로 구매한 경우와 이전 요청을 재전송한 경우를 구분할 수 없습니다. 그래서 한 번의 구매 의도마다 요청 ID를 부여하고, 재전송할 때는 그 ID를 그대로 사용합니다.

```text
서버 의사코드 · 단일 트랜잭션 저장소 가정
(계정 ID, 요청 ID)의 유일성 제약으로 동시 요청을 조정
기존 완료 요청이면 원래 상품·수량의 일치를 확인하고 저장된 결과 반환
새 요청이면 서버 가격·잔액·재고 검증
같은 트랜잭션에서 차감 + 지급 + 처리 결과 기록
커밋 후 클라이언트에 결과 응답
```

차감·지급·결과 기록을 **하나의 트랜잭션**으로 묶는다는 말은 세 변경을 모두 확정하거나 모두 되돌린다는 뜻입니다. 구매 버튼을 잠그면 연타는 줄일 수 있지만 재접속 뒤 같은 요청이 다시 들어오는 상황은 여전히 남습니다.

**더 생각해 보기**　차감과 지급을 서로 다른 서비스가 맡는다면 위 예시의 가정이 깨집니다. 어디까지 처리했는지 남기고, 각 단계에서 같은 요청이 다시 들어왔을 때와 한쪽만 성공했을 때의 처리 방법을 정해야 합니다.

## 6. 데이터 주도 설계와 비동기 처리 · B 카드에 A 아이콘이 뜨는 이유는?

기획자가 미션 목표를 코어 세 개에서 두 개로 바꿉니다. 이때 위젯 코드까지 고쳐야 할까요? 목표 개수와 안내 문구는 **미션 정의**, 이번 판에서 확보한 코어 목록은 **진행 상태**, HUD의 ‘1/2 확보’는 **표시값**으로 나누어 봅시다. 그러면 기획자는 정의만 고치고 화면은 바뀐 값에서 문구를 만들 수 있습니다. 미션 ID는 번역해도 변하지 않는 값으로 정합니다. 목표가 0이거나 맵에 배치된 코어 수보다 많으면 시작 전에 알려 줍니다.

**아이콘이 뒤바뀌는 과정을 따라가 봅시다.**

1. 목록의 첫 카드가 아이템 A의 아이콘을 요청합니다. 로딩이 끝날 때까지 화면은 다른 작업을 계속합니다. 이것이 비동기 로딩입니다.
2. 플레이어가 스크롤합니다. 목록은 같은 카드 위젯을 아이템 B에 재사용하고 B의 아이콘을 요청합니다.
3. B의 아이콘이 먼저 도착합니다. 뒤늦게 도착한 A의 결과까지 적용하면 B 카드에 A가 보입니다.

카드에 새 아이템을 연결할 때마다 번호를 올리고, 로딩 완료 시 요청 당시 번호와 현재 번호가 일치하는지 검사합니다. 위젯이 아직 유효한지도 함께 확인합니다. 카드를 닫을 때도 이전 요청을 무효화합니다. 에디터에서는 보이는데 패키지 빌드에서만 아이콘이 항상 비어 있다면, 에셋이 배포용 데이터에 포함됐는지도 확인하세요.

## 7. UMG·MVVM · HP 한 칸이 변하면 어디까지 갱신해야 하는가?

체력 바를 예로 들어 MVVM의 역할을 나눠 봅시다. **모델(Model)**은 현재 체력과 최대 체력을 보관합니다. **뷰모델(ViewModel)**은 두 값으로 막대를 얼마나 채울지 계산합니다. **뷰(View)**는 그 비율만큼 막대를 그립니다. 플레이어가 회복 버튼을 누르면 게임 규칙이 회복량을 확정한 다음 화면이 갱신됩니다.

UMG에서 매 프레임 값이 바뀌었는지 조회하는 방식과, 값이 바뀐 순간에만 변경을 알리는 방식은 비용이 다릅니다. UE의 `FieldNotify`는 이런 변경을 구독자에게 알릴 때 사용합니다. 아래 함수는 뷰모델에 들어갈 계산만 뽑은 예입니다.

```cpp
// C++17 계산부. <algorithm> 필요. 최대 HP가 0이면 빈 막대로 표시하는 정책.
float HealthFraction(float current, float maximum)
{
    if (maximum <= 0.0f)
        return 0.0f;
    return std::clamp(current / maximum, 0.0f, 1.0f);
}
```

현재 체력이 50이고 최대 체력이 100이면 함수는 0.5를 반환합니다. 버프로 최대 체력만 200이 되면 반환값은 0.25입니다. 현재 체력 변경만 구독한 위젯은 여전히 절반이 찬 막대를 보여 줍니다. **계산 결과에 영향을 주는 두 값 모두** 갱신의 계기가 되어야 합니다.

상점 카드와 미션 카드를 함께 만들 때는 선택 테두리, 잠금 표시, 로딩 표시를 공용 위젯에 둘 수 있습니다. 구매 가능 여부는 상점 모델이, 목표 달성 여부는 미션 모델이 정합니다. 고정 조준점처럼 표시할 값이 거의 없는 위젯은 별도 뷰모델을 두는 이득이 작습니다.

## 8. 입력 라우팅과 설정 · 모달을 닫았는데 총도 발사된 이유는?

패드에서 확인 버튼을 눌러 설정 창을 닫았는데, 게임으로 돌아오자마자 총이 발사됩니다. 원인을 찾으려면 버튼을 누른 순간과 뗀 순간을 나누어 보세요. 창이 닫히면서 뒤따르는 입력을 게임 화면이 받았을 수 있습니다.

**입력 라우팅**은 버튼 입력을 어느 화면이나 기능에 전달할지 정하는 과정입니다. **포커스**는 그 화면 안에서 현재 조작할 항목을 가리킵니다. CommonUI에서는 어느 화면이 활성 상태인지, 어떤 자식 위젯에 포커스가 있는지, 누가 입력을 처리했는지를 차례로 확인합니다.

| 전환 | 기대 동작 | 실패 진단 |
|---|---|---|
| 패드로 목록 → 상세 | 사용 가능한 첫 버튼에 포커스 | 숨겨진 배경 목록이 입력을 소비하는지 확인 |
| 상세 → 목록 | 원래 카드로 복귀, 삭제됐다면 인접 유효 항목 선택 | 복귀 대상을 위젯 주소로만 기억했는지 확인 |
| 마우스로 열고 패드로 탐색 | 패드 아이콘과 실제 포커스 모두 유효 | 장치 인식과 포커스 배정을 각각 확인 |
| 설정 → 취소 | 초안 폐기, 미리 적용한 음량 복구 | 편집값·현재 적용값·저장값이 섞였는지 확인 |

설정의 ‘취소’를 구현할 때는 세 값을 나눠 생각하면 편합니다. 슬라이더로 편집 중인 음량, 스피커에서 지금 들리는 음량, 다음 실행에도 사용할 저장값입니다. 미리 듣기를 지원한다면 취소할 때 슬라이더와 실제 음량을 모두 되돌려야 합니다.

전적 화면에서도 값의 의미를 먼저 정합니다. ‘부활 횟수’ 항목을 이번 패치에 추가했다면 이전 경기 기록에는 이 값이 없습니다. 이를 모두 0회로 표시하면 실제로 한 번도 부활하지 않은 경기와 섞여 평균이 달라집니다. 이전 기록에 쓸 표시와 집계 기준을 함께 정합니다.

## 9. 인게임 시스템 · 같은 장면을 누구의 시간에서 보는가?

한 팀원이 쓰러진 장면을 떠올려 보세요. 관전자는 살아 있는 동료가 지금 보는 장면을 보고 싶습니다. 리플레이를 돌려 보는 사람은 30초 전 그 순간의 장면을 원합니다. 둘 다 다른 플레이어를 화면에 보여 주지만, 읽어 와야 할 데이터의 시점이 다릅니다.

| 시스템 | 이론 | 게임에서 답할 문제 |
|---|---|---|
| 관전 | 플레이어 신원과 Pawn 수명 분리 | 관전 대상이 이탈하면 누구에게 전환하며, 이전 HP 구독은 언제 정리하는가? |
| 리플레이 | 기록된 상태를 재생 시간축에서 복원 | 30초로 탐색해 당시 점수판을 복원하면서 실제 계정 보상 재지급을 어떻게 방지하는가? |
| 팀 핑 | 발신 권한·공간 기준·만료 시각 | 움직이는 적이 사라지면 마지막 위치에 남길까? 늦게 받은 핑의 잔여 시간은 어느 시계로 계산할까? |
| 튜토리얼 | 안내 노출 조건과 완료 조건 분리 | 재장전을 먼저 한 사용자가 나중에 안내를 받으면 소급 완료할까? |
| 보스 | 단계 전이와 일회성 진입 효과 분리 | HP가 75%에서 35%로 떨어지면 중간 단계를 건너뛸까? 중간 참가자에게 어떤 연출을 보일까? |

관전 중에는 지금 진행 중인 경기에서 카메라가 따라갈 대상을 바꿉니다. 리플레이에서 30초 지점으로 이동하면 그 시각의 점수와 목표 진행도까지 화면에 다시 그려야 합니다. 점수판이 실시간 득점 알림만 받아 숫자를 올리는 구조라면, 과거 시점으로 건너뛴 직후에는 점수를 복원할 수 없습니다. 언리얼의 `DemoNetDriver`가 기록하는 데이터와 클라이언트가 화면에서만 만든 표시를 구분해 보세요.

## 10. 디버깅·협업·AI 검증 · 결과 창을 세 번 열면 보상음이 세 번 난다

결과 창을 세 번 열었다 닫은 뒤 코어를 확보했더니 완료음이 세 번 들립니다. 가능한 원인은 여러 가지입니다. 서버가 보상을 세 번 지급했을 수도 있고, 같은 위젯이 변경 알림을 세 번 등록했을 수도 있고, 소리 재생 코드가 반복됐을 수도 있습니다.

같은 미션 ID를 기준으로 서버의 지급 기록, 클라이언트의 상태 변경 통지 횟수, 위젯의 콜백 호출 횟수를 비교하세요. 결과가 각각 1회, 1회, 3회라면 통지 한 건을 어떤 위젯들이 받았는지부터 좁혀 갑니다. AI가 ‘약한 참조를 썼으니 안전하다’고 설명해도, 살아 있는 위젯이 같은 알림을 여러 번 등록한 경우까지 설명할 수 있는지 확인해야 합니다.

| 검증 범위 | 시험 | 잡을 수 있는 오류 |
|---|---|---|
| 규칙 단위 | A,A,B,B에서 완료 전이 횟수 확인 | 중복 집계 |
| UI 통합 | 열기·닫기 3회 뒤 모델 변경 1회 | 콜백 누적 |
| 패키지 2인 | 결과 전환 중 합류하고 패드로 복귀 | 초기 상태 누락, 포커스 유실 |
| 성능 | 동일 부하에서 트레이스 전후 비교 | 반복 레이아웃 비용, 첫 열기 hitch |

기획자와는 플레이어가 경험할 동작을 먼저 합의합니다. 예를 들어 ‘완료 순간에 접속해 있던 사람만 소리를 한 번 듣고, 뒤늦게 합류한 사람은 완료된 목표만 본다’고 정할 수 있습니다. 코드 리뷰에는 이 규칙을 어긴 재현 순서와 단계별 호출 횟수를 남겨 둡니다. 수정한 뒤 같은 순서로 다시 시험하면 의도한 부분이 고쳐졌는지 확인할 수 있습니다.

# 종합 평가 · IDE 없이 풀기

**상황** 마지막 코어 확보와 동시에 게스트가 들어왔다. 호스트는 완료음을 두 번 듣고 게스트는 0/2를 본다. 옵션을 닫자 게스트 화면이 2/2로 바뀐다.

1. 이 관찰로 실제 보상도 두 번 지급됐다고 결론낼 수 있는가?
2. 게스트 화면이 옵션을 닫고 회복됐다는 사실이 지지하는 가설은? 무엇을 기록하면 이 가설을 반박할 수 있는가?
3. 코어 판정, 공유 진행도, 패드 포커스, 영속 보상 각각을 누가 보유할지 정하라.
4. 기획자가 목표 수를 바꿀 때 검증할 두 경계값을 제시하라.

**풀이**

1. 소리를 두 번 들었다는 사실만으로 지급 횟수는 알 수 없습니다. 서버 지급 기록과 클라이언트 소리 재생 기록을 각각 확인합니다.
2. 옵션을 닫을 때 화면이 최신 값을 다시 읽었을 수 있습니다. 닫기 직전 게스트 모델이 이미 2/2였다면 HUD의 초기 읽기나 알림 연결을 살핍니다. 모델도 0/2였다면 서버에서 클라이언트까지 값이 전달된 시점을 추적합니다.
3. 서버가 코어 확보를 판정하고, 복제되는 게임 상태가 공동 진행도를 보관합니다. 포커스는 각 플레이어의 UI가 관리하고, 계정 보상은 권한 있는 저장소에 남깁니다.
4. 목표가 0개일 때와 맵에 배치된 코어 수보다 많을 때를 확인합니다. 시작한 판에도 목표 변경을 적용할지는 기획과 별도로 정합니다.

**권장 순서** 이미 2인 패키지와 중도 합류를 검증한 경험을 살려 3 → 7 → 8 → 10장을 먼저 읽는다. 다음으로 1·2·5·6장에서 수명·규칙·데이터를 점검하고 4·9장과 종합 평가로 마무리한다. 더 읽을 때는 공개 게임 Lyra에서 화면 하나만 골라 생성 → 활성화 → 입력 → 비활성화 경로를 설명해 본다. 실제 API는 사용하는 프로젝트 버전의 헤더와 대조한다.
